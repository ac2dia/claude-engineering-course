# 이벤트 기록과 상태 변경을 원자적으로 구현하기

## 작은 루프 1. 처리 결과를 기록합니다

```text
중복 Webhook 실패 테스트 하나만 통과시키세요.
eventId를 primary key로 갖는 수신 이벤트 기록을 추가하고,
처리 결과(PROCESSED 또는 IGNORED)와 무시 이유를 조회 가능하게 남기세요.
집중 테스트와 diff를 보고한 뒤 멈추세요.
```

`DUPLICATE`는 저장된 원본 결과가 아니라 재수신 요청에 대한 응답입니다. DB에는 최초 이벤트의 실제 처리 결과가 남아야 운영자가 무엇이 일어났는지 추적할 수 있습니다.

## 작은 루프 2. transaction 실패 후 재수신을 보장합니다

```text
처리 도중 실패와 재수신 테스트를 통과시키세요.
이벤트 기록, payment 변경, order 변경은 같은 transaction에서 commit되거나 rollback되어야 합니다.
실패한 이벤트를 PROCESSED로 남기지 마세요.
집중 테스트를 실행하고 transaction 경계를 설명한 뒤 멈추세요.
```

검토 포인트:

- 이벤트 기록만 먼저 별도 transaction으로 확정하지 않는가?
- 실패 exception을 catch한 뒤 성공 응답으로 바꾸지 않는가?
- rollback 뒤 같은 event ID가 다시 진입할 수 있는가?
- 동시 중복에서 DB의 event ID unique constraint가 최종 방어선인가?
- unique 충돌을 rollback된 transaction 밖에서 해석하는가?

## 작은 루프 3. 처리와 무시를 구분합니다

```text
이미 APPROVED인 payment에 다른 eventId의 승인 이벤트가 오면
상태를 다시 변경하지 말고 IGNORED와 이유를 기록하세요.
그 테스트와 전체 Webhook 테스트를 실행한 뒤 멈추세요.
```

<LearningNote id="session-06-atomic-boundary" prompt="이벤트 기록과 도메인 변경이 같은 transaction이어야 하는 이유, 중복과 재시도의 차이를 설명하세요." multiline />

## 범위 경계

이번 세션은 승인 이벤트의 중복과 재수신에 집중합니다. 서명 검증, timestamp 허용 범위, Webhook secret 회전, 비동기 queue와 잘못된 이벤트 순서는 후속 주제입니다. Claude가 이 기능까지 확장하면 제안 목록으로 돌리고 현재 실패 테스트에 필요한 최소 변경만 유지하세요.

## 완료 조건

- [ ] 첫 이벤트는 `PROCESSED`이고 상태 변경이 한 번 일어난다.
- [ ] 같은 event ID 재수신은 `DUPLICATE`이고 기록은 한 건이다.
- [ ] 처리 실패 시 이벤트와 도메인 변경이 모두 rollback된다.
- [ ] 실패한 동일 이벤트의 재수신은 정상 처리된다.
- [ ] 무시한 새 이벤트도 이유와 함께 추적된다.
