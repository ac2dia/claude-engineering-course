# 불확실성을 보존하고 후속 확인하기

## 구현 계약을 먼저 고정합니다

| 상황 | 기대 결과 |
|---|---|
| PSP 승인 응답 정상 수신 | payment `APPROVED`, order `PAID` |
| PSP 승인 후 응답 유실 | HTTP 202, payment `UNKNOWN`, order `PENDING_PAYMENT` |
| 같은 key 재전송 | 같은 payment ID와 `UNKNOWN`, PSP 추가 호출 없음 |
| 후속 PSP 조회에서 승인 확인 | payment `APPROVED`, order `PAID` |

`UNKNOWN`은 실패의 다른 이름이 아닙니다. 외부 시스템의 결과를 아직 확정할 증거가 없음을 나타냅니다.

## 작은 루프 1. 결함 테스트를 원하는 행동으로 바꾸기

```text
PspTimeoutCharacterizationTest의 기존 결함 assertion을 다음 기대 행동으로 바꾸세요.
- timeout 결과는 UNKNOWN이다.
- payment row는 유지된다.
- order는 아직 PENDING_PAYMENT다.
- 같은 key 재전송은 같은 payment를 반환하고 PSP charge는 한 번이다.

제품 코드는 수정하지 말고 테스트가 기대한 이유로 실패하는지 보고한 뒤 멈추세요.
```

## 작은 루프 2. PSP 호출과 로컬 상태 경계 분리

```text
위 두 실패 테스트만 통과시키는 최소 구현을 하세요.
PSP 호출 전에 PROCESSING payment가 독립적으로 commit되어야 하고,
응답 유실이면 별도 transaction에서 UNKNOWN으로 바뀌어야 합니다.
timeout을 FAILED로 단정하거나 PSP를 다시 호출하지 마세요.

집중 테스트와 diff를 보고한 뒤 멈추세요.
```

검토 포인트:

- 같은 클래스 내부 호출 때문에 `@Transactional` proxy가 우회되지 않는가?
- 외부 네트워크 호출을 긴 DB transaction 안에 계속 잡아두지 않는가?
- timeout catch 뒤 상태 변경이 실제로 commit되는가?
- `UNKNOWN` 재전송 경로가 PSP 호출로 돌아가지 않는가?

## 작은 루프 3. 후속 조회로 확정

```text
UNKNOWN payment의 payment ID로 PSP 상태를 조회하는 provider 계약과
후속 확인 use case를 추가하세요.
PSP가 APPROVED라고 응답할 때만 payment와 order를 승인 상태로 바꾸세요.
확인 API의 통합 테스트를 먼저 실패시키고 최소 구현 후 전체 테스트를 실행하세요.
```

운영 서비스에서는 후속 확인을 scheduler, queue 또는 수동 운영 도구가 호출할 수 있습니다. 이번 실습은 상태 전이와 검증에 집중하기 위해 `POST /api/payments/{paymentId}/confirm` 형태의 명시적 진입점을 사용해도 충분합니다.

## 완료 조건

- [ ] 응답 유실 뒤 payment가 `UNKNOWN`으로 남는다.
- [ ] order를 섣불리 `PAID` 또는 실패로 확정하지 않는다.
- [ ] 같은 key 재전송이 PSP를 다시 호출하지 않는다.
- [ ] 후속 조회가 승인 근거를 얻은 뒤에만 두 로컬 상태를 변경한다.
- [ ] 기존 정상 결제와 멱등성 테스트가 모두 통과한다.

## 중단 조건

Claude가 retry library, message broker, scheduler, 범용 state machine을 추가하려 한다면 멈추고 이번 테스트에 필요한 최소 상태와 조회 계약만 남기게 하세요. 운영 확장안은 구현이 아니라 후속 제안으로 기록합니다.
