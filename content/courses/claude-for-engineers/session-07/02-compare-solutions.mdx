# 해결안과 트레이드오프 비교하기

## 하나의 답 대신 선택지를 요청합니다

```text
상태 역행을 막는 대안을 최소 3개 제시하세요.
각 대안을 다음 기준으로 비교하고 아직 구현하지 마세요.

- 필요한 PSP 데이터와 그 신뢰 가정
- 허용·거부 전이를 표현하는 명확성
- 중복과 순서 역전에서의 정확성
- 운영자가 무시 이유를 추적할 수 있는가
- 현재 코드 규모에서의 복잡도와 변경 범위
- 새로운 실패 모드
```

대표적인 대안은 다음과 같습니다.

| 대안 | 장점 | 위험 또는 전제 |
|---|---|---|
| 수신 timestamp가 최신인 이벤트 적용 | 구현이 작아 보임 | 수신 순서는 발생 순서가 아님 |
| 상태에 숫자 우선순위 부여 | 역행 차단이 단순함 | 승인과 거절은 일반적인 대소 관계가 아님 |
| 명시적 허용 전이 표 | 도메인 규칙과 테스트가 읽힘 | 상태·이벤트 추가 시 표를 갱신해야 함 |
| 범용 state machine 도입 | 전이가 많을 때 확장 가능 | 현재 범위에는 설정과 추상화가 과할 수 있음 |

## Claude의 제안에 반대할 때

“그건 싫어요” 대신 반례와 선택 기준을 제시합니다.

```text
수신 timestamp 비교는 채택하지 않겠습니다.
이 티켓은 늦게 수신된 이벤트가 더 오래된 PSP 결과일 수 있음을 전제로 합니다.
수신 시각이 PSP 발생 순서를 증명하지 못하는 반례를 반영해 대안을 다시 평가하세요.
현재 두 종결 상태와 두 이벤트에 필요한 최소 규칙을 표로 제시하세요.
```

또는 과도한 state machine이 제안됐다면:

```text
현재 필요한 상태와 이벤트 수, 변경 빈도를 근거로 라이브러리 도입 비용을 설명하세요.
같은 규칙을 Java의 명시적 정책 클래스와 표 기반 테스트로 표현한 안도 함께 비교하세요.
```

## 이번 실습의 정책

| 현재 상태 | APPROVED 이벤트 | DECLINED 이벤트 |
|---|---|---|
| `PROCESSING` | 적용 | 적용 |
| `UNKNOWN` | 적용 | 적용 |
| `APPROVED` | 무시·이유 기록 | 무시·이유 기록 |
| `DECLINED` | 무시·이유 기록 | 무시·이유 기록 |

이 표가 모든 결제 서비스의 정답은 아닙니다. 이번 교육용 도메인에서는 `APPROVED`와 `DECLINED`를 종결 상태로 고정합니다. 실제 PSP가 reversal, capture, refund 또는 상태 version을 제공한다면 정책은 달라져야 합니다.
