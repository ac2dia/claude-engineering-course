# 전체 diff 검증과 네 번째 원칙

## 테스트 통과 후가 리뷰의 시작입니다

다음 명령을 직접 실행합니다.

```bash
./gradlew test
git status --short
git diff --stat lab-04-start
git diff lab-04-start
```

Claude에게도 전체 diff를 읽게 할 수 있지만 최종 판단은 직접 합니다.

```text
lab-04-start 이후 전체 diff를 읽고 다음만 보고하세요.
- 완료 조건별 구현과 테스트 근거
- 계획에 없던 변경
- 중복 코드와 불필요한 추상화
- transaction, DB constraint와 동시성 위험
- 테스트하지 않은 실패 경로

코드는 수정하지 말고 파일 경로와 근거를 제시하세요.
```

## 독립 리뷰 체크리스트

### 정확성

- [ ] 같은 key의 재전송이 최초 payment ID를 반환한다.
- [ ] 다른 주문 충돌이 PSP 호출 전에 차단된다.
- [ ] unique constraint 이름과 대상 column이 명확하다.
- [ ] 경쟁에서 진 transaction이 rollback된 뒤 결과를 다시 읽는다.

### 범위

- [ ] key 만료와 PSP timeout을 임의로 구현하지 않았다.
- [ ] 교육용 요구사항에 없는 Redis나 분산 lock을 추가하지 않았다.
- [ ] 기존 provider와 pricing 모듈을 불필요하게 바꾸지 않았다.

### 테스트

- [ ] response, DB row와 PSP 호출 횟수를 함께 검증한다.
- [ ] 동시 요청이 실제로 별도 thread에서 실행된다.
- [ ] 전체 테스트가 통과한다.
- [ ] 테스트를 약화하거나 건너뛰지 않았다.

## 참고 구현과 비교

자신의 구현과 리뷰를 끝낸 뒤에만 비교하세요.

```bash
git diff lab-04-reference -- src/main src/test
git show --stat lab-04-reference
```

참고 구현은 유일한 정답이 아닙니다. 구조가 다르다면 다음을 비교합니다.

- 같은 실패 조건을 보장하는가?
- transaction 실패 후 재조회가 가능한가?
- 데이터베이스가 최종 정합성을 보장하는가?
- 더 단순한 구조라면 무엇을 포기하거나 개선했는가?
