# 요구사항을 행동 표로 바꾸기

## Claude 학습 목표

- 해결책보다 먼저 관찰 가능한 행동을 정의합니다.
- 티켓의 문장을 결정된 요구사항, 가정, 미결 질문으로 분리합니다.
- Claude가 질문하도록 요청하되 최종 제품 판단은 개발자가 확인합니다.

## 시작 업무 사례

Session 3에서는 실습 저장소의 다음 티켓을 사용합니다.

```text
docs/tickets/payment-idempotency.md
```

핵심 요청은 짧습니다.

```text
클라이언트가 idempotency key를 보내면 네트워크 재시도 때문에
동일한 결제가 중복 승인되지 않아야 합니다.
```

이 문장만으로는 구현 완료 여부를 테스트할 수 없습니다. “동일한 결제”, “재시도”, “결과를 돌려준다”가 구체적으로 무엇인지 정해야 하기 때문입니다.

## 해결책보다 행동 예시가 먼저입니다

다음 네 상황을 입력, 기존 상태, 기대 응답과 PSP 호출 횟수로 표현합니다.

| 상황 | 입력에서 달라지는 것 | 결정해야 할 행동 |
|---|---|---|
| 최초 요청 | 새로운 key와 주문 | 생성 상태와 HTTP 응답 |
| 같은 요청 재전송 | 같은 key, 같은 주문 | 기존 결과 재사용 여부 |
| 충돌 요청 | 같은 key, 다른 주문 또는 다른 값 | 오류 조건과 응답 |
| 동시 요청 | 같은 key가 거의 동시에 도착 | 한 건만 처리하는 보장 방법 |

<LearningNote id="session-03-behavior-matrix" prompt="네 상황의 기대 행동을 자신의 말로 작성하세요." multiline />

## 세 종류의 문장을 분리합니다

```text
[결정됨] 같은 key와 같은 주문은 최초 결과를 돌려준다.
[미결] key는 모든 요청에 필수인가?
[가정] key는 주문마다 유일하며 24시간 보관한다.
```

가정은 요구사항이 아닙니다. 작업을 진행하기 위해 임시로 선택했다면 누가 확인해야 하는지와 틀렸을 때 바뀌는 설계도 함께 기록합니다.

## Claude에게 답보다 질문을 요청할 수 있습니다

Claude Code 공식 Best Practices는 큰 기능에서 Claude가 먼저 요구사항을 인터뷰하도록 요청하는 방식을 소개합니다. 이번 실습에서는 질문을 많이 만드는 것이 목적이 아니라, 구현과 테스트를 바꿀 중요한 결정을 찾는 것이 목적입니다.

```text
아직 구현 계획을 쓰지 마세요.
이 티켓의 완료 조건을 확정하려면 제품 담당자에게 물어야 할 질문을 정리하세요.
각 질문에는 답이 달라질 때 영향받는 동작이나 테스트를 한 줄로 설명하세요.
코드에서 답할 수 있는 질문은 별도 목록으로 분리하세요.
```
