# 개념 확인과 세 번째 원칙

## 개념 확인

### 1. 같은 key를 먼저 조회하고 없으면 결제를 생성하면 동시 요청도 안전한가요?

<details>
<summary>정답 확인</summary>

반드시 그렇지는 않습니다. 두 요청이 거의 동시에 조회하면 둘 다 key가 없다고 판단할 수 있습니다. 데이터베이스 unique constraint 같은 경쟁 상황의 최종 보장과 충돌 처리 전략을 함께 검토해야 합니다.

</details>

### 2. 티켓에 없는 key 유효 기간을 Claude가 24시간으로 정했다면 어떻게 해야 하나요?

<details>
<summary>정답 확인</summary>

확정 요구사항으로 받아들이지 않습니다. 제품 결정이 필요한 질문 또는 명시적인 임시 가정으로 남기고, 값이 달라질 때 영향을 받는 저장·조회·정리 정책을 기록합니다.

</details>

### 3. 좋은 구현 계획의 가장 중요한 특징은 무엇인가요?

1. 수정할 파일을 최대한 많이 나열한다.
2. 최신 기술과 확장 가능한 추상화를 포함한다.
3. 각 단계가 요구사항·코드 근거·실패 테스트와 연결된다.

<details>
<summary>정답 확인</summary>

3번입니다. 계획은 그럴듯한 설계 문서가 아니라 구현 중 방향을 확인하고 결과를 검증할 수 있는 작업 단위여야 합니다.

</details>

## 계획 품질 자기 평가

각 항목을 0~2점으로 평가하세요.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 요구사항 | 기능 이름만 있음 | 일부 행동 정의 | 모든 핵심 행동과 연결 |
| 근거 | 파일 추측 | 경로만 있음 | 현재 책임과 코드 위치 확인 |
| 불확실성 | 숨겨진 가정 | 가정 표시 | 질문·가정·영향 분리 |
| 검증 | 전체 테스트만 실행 | 정상 테스트 포함 | 실패·경쟁·호출 횟수 포함 |
| 범위 | 과도한 확장 | 일부 선택 사항 혼재 | 최소 변경과 확장 분리 |
