# 메모리와 CLAUDE.md 설계하기

## 네 가지를 구분합니다

| 개념 | 무엇인가 | 주의점 |
|---|---|---|
| 현재 컨텍스트 | 이번 대화, 읽은 파일, 도구 출력 | 길이 제한이 있고 요약될 수 있음 |
| 세션 기록 | 재개 가능한 이전 대화 | 새 세션이 자동으로 모두 기억하지 않음 |
| `CLAUDE.md` | 사람이 작성한 지속 프로젝트 지침 | 컨텍스트이지 강제 정책이 아님 |
| auto memory | Claude가 작업에서 기록한 메모 | 내용과 적용 범위를 `/memory`로 검토해야 함 |

Claude Code의 각 새 세션은 새로운 컨텍스트로 시작합니다. “지난번에 말했으니 알겠지”보다 반복적으로 필요한 사실을 올바른 범위의 파일에 기록합니다.

## 지침 파일의 범위

| 위치 | 적합한 내용 |
|---|---|
| 조직 managed policy | 중앙 관리가 필요한 공통 정책 |
| `~/.claude/CLAUDE.md` | 모든 프로젝트에 적용할 개인 선호 |
| 저장소 `CLAUDE.md` 또는 `.claude/CLAUDE.md` | 팀과 공유할 빌드·검증·아키텍처 지침 |
| `CLAUDE.local.md` | 커밋하지 않을 개인 프로젝트 메모 |
| `.claude/rules/` | 경로나 주제별로 나눈 규칙 |

`/memory`로 현재 세션에 어떤 파일과 메모리가 로드되었는지 확인하고, `/init`은 초안을 만드는 출발점으로만 사용합니다. 생성된 내용을 코드 리뷰하듯 검토하세요.

## 좋은 CLAUDE.md의 기준

- **구체적**: “테스트 잘 작성”보다 실행 명령과 핵심 assertion을 적습니다.
- **검증 가능**: Claude와 개발자가 같은 완료 조건을 확인할 수 있습니다.
- **현재 상태와 일치**: 실제 없는 모듈·명령·규칙을 방치하지 않습니다.
- **간결**: 자주 필요한 내용만 두고 상세 설명은 문서 링크로 연결합니다. 공식 문서는 대략 200줄 미만을 목표로 검토하라고 안내합니다.
- **구조화**: 빌드, 아키텍처, 코딩 규칙, 금지 행동을 제목으로 나눕니다.
- **보안 분리**: 토큰, 비밀, 고객 데이터는 넣지 않습니다.
- **강제 장치와 구분**: 반드시 막아야 하는 행동은 CI, 권한, hooks, managed settings 같은 별도 통제를 사용합니다.

## 나쁜 예와 개선 예

나쁜 예:

```markdown
# Instructions
- 좋은 코드를 작성한다.
- 모든 테스트를 돌린다.
- 결제는 조심한다.
```

개선 예:

```markdown
# Build and verification
- JDK 21을 사용한다.
- 집중 테스트 후 `./gradlew test`를 실행한다.
- 완료 보고에 실행한 명령, 결과, 실행하지 못한 검증을 구분한다.

# Architecture
- `order`, `payment`, `provider`, `pricing`, `shared`는 모듈 경계다.
- PSP timeout은 실패로 단정하지 말고 승인 여부가 불확실한 상태로 다룬다.

# Working agreement
- 구현 전에 관련 흐름과 테스트를 조사한다.
- 코드로 확인하지 못한 운영 사실은 가정으로 표시한다.
- 외부 호출, 배포, 원격 push는 개발자의 명시적 승인 전에 실행하지 않는다.
```
